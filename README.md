# لمسة — Lamssa

منتج لإدارة عيادات التجميل بواجهة **عربية أولًا وباتجاه RTL**، يستهدف عيادات مستقلة
متعددة بهوية بصرية خاصة لكل عيادة. الواجهة الحالية نموذج متقدم باستخدام React
وTypeScript وVite؛ الخادم NestJS مع PostgreSQL وPrisma، والمصادقة والجلسات
واختيار العيادة والصلاحيات وعزل البيانات مضافة، مع إدارة المرضى الإدارية في الخطوة 1.5،
وجدولة المواعيد وإدارة الموارد في الخطوة 1.6، والزيارات والانتظار المباشر في الخطوة 1.7،
والفوترة والمدفوعات في الخطوة 1.8، وإدارة هوية العيادة وفريقها في الخطوة 1.9،
والتدقيق المركزي والنسخ الاحتياطي المشفر في الخطوة 2.1، والمصادقة متعددة العوامل (MFA) وتأكيد الصلاحيات الحساسة في الخطوة 2.2،
وحوكمة البيانات وحفظها وإدارة طلبات الخصوصية وتصدير البيانات الآمن في الخطوة 2.3،
والمراقبة الهيكلية وتتبع الأخطاء والتنبيهات الموثوقة ومعالجة أخطاء الواجهة في الخطوة 2.4،
وبنية النشر والحاويات والوكيل العكسي والتحقق الإنتاجي المعزول في الخطوة 2.5.

**لا تُدخل بيانات مرضى حقيقية.** تسجيل الدخول واختيار العيادة يتصلان بالخادم،
وسجل المرضى الإداري والمواعيد والموارد والزيارات والانتظار والفواتير والمدفوعات وطلبات الخصوصية وسياسات الاستبقاء والمقاييس محفوظون لكل عيادة عبر API وصلاحيات العضوية وFORCE RLS.
ملخص اللوحة والعرض القديم الاختياري يبقيان بيانات محلية تجريبية مشتركة بين
اختيارات العيادات في هذا المتصفح. لا يوجد استيراد تلقائي لمرضى أو مواعيد العرض القديم.
لا توجد سجلات علاجية أو صور طبية؛ السجلات الحالية إدارية بحتة.

## المراقبة، تتبع الأخطاء والموثوقية — الخطوة 2.4

توفر المنصة بنية رصد وموثوقية مدمجة دون أي تكاليف أو اشتراكات خارجية:
1. **التسجيل الهيكلي وحجب البيانات الشخصية (Structured JSON Logging & Redaction)**:
   - سجلات JSON أحادية السطر تدعم التجميع عبر Vector أو Loki.
   - حجب عناوين الشبكة للمحافظة على الخصوصية (IPv4 `/24` و IPv6 `/48`).
   - حجب تلقائي لكلمات المرور، والرموز، وبيانات البطاقات، والمعلومات الطبية في السجلات والترويسات.
2. **المقاييس التشغيلية بصيغة بروميثيوس (Prometheus Metrics & Diagnostic Endpoints)**:
   - متابعة حجم الطلبات، وفئات الردود (`2xx`, `3xx`, `4xx`, `5xx`)، والطلبات النشطة، ومحاولات الدخول الفاشلة.
   - قياس دقيق لنسب زمن الاستجابة ($p50$, $p95$, $p99$, $max$).
   - تصدير المقاييس بصيغة بروميثيوس عبر مسار `GET /api/v1/metrics`.
   - مسارات تشخيص ومراقبة الجاهزية والحيوية والتنبيهات النشطة.
3. **تتبع الأخطاء المنفصل والتنبيهات الذكية (Decoupled Error Tracking & Alerting)**:
   - توليد بصمات SHA-256 محددة لتجميع الأخطاء المتكررة وعزل المتغيرات العشوائية.
   - محرك تنبيهات تشغيلي ذكي مع فترة تهدئة 15 دقيقة لمنع تكرار الإشعارات وحلها تلقائيًا عند التعافي.
4. **حاجز معالجة أخطاء الواجهة (Arabic RTL Error Boundary)**:
   - حماية واجهة React من الانهيار الكامل مع رمز تتبع فريد (`ERR-XXXXXX`) يظهر للمستخدم للدعم الفني.
   - أزرار استعادة تفاعلية وآمنة باللغة العربية.

تفاصيل المقاييس وإعدادات بروميثيوس وأدلة التشغيل في [دليل المراقبة والموثوقية](docs/monitoring-reliability.md).

## النشر والتحقق الإنتاجي — الخطوة 2.5

أضيفت صور إنتاج متعددة المراحل للويب وAPI، وCompose مرحلي مع PostgreSQL على شبكة
داخلية بلا منفذ عام، وCaddy لإنهاء TLS والتحقق من المضيف والترويسات وحدود الرفع.
المقاييس محجوبة عند الوكيل العام؛ يقرأها مراقب داخلي بمفتاح آلة مستقل، بينما
التشخيص والتنبيهات العامة للمنصة مقتصرة على مدير منصة نشط ولا تمنح عضوية العيادة
أي وصول. Docker وCaddy اختياريان ولم يحلا محل مسار PostgreSQL المحلي للتطوير.

أُنجز التحقق المعزول عبر HTTPS والاستعادة المشتركة لقاعدة البيانات وملفات الهوية.
يفحص `npm run test:deployment-runtime` الحاويات المرحلية القائمة دون تعديل بياناتها؛
لا تُمرر أسرار مدير قاعدة البيانات أو الترحيلات إلى حاوية API. يوضح دليل النشر
نتائج التحقق الفعلية ومتطلبات الموافقة الباقية قبل إطلاق عام.

التفاصيل والأوامر والمفاضلات في [دليل النشر](docs/deployment.md)، وبوابات الإطلاق في
[قائمة الجاهزية](docs/production-readiness-checklist.md). لا ينفّذ هذا المستودع نشرًا
عامًا أو DNS أو شهادات أو شراء موارد.

## الخصوصية وحوكمة البيانات — الخطوة 2.3

توفر المنصة في لوحة إعدادات العيادة (تبويب «الخصوصية والحوكمة») أدوات متكاملة لإدارة حوكمة البيانات:
1. **سجل طلبات حقوق الخصوصية (Privacy Requests)**:
   - متابعة طلبات المرضى للوصول (Access)، والتصحيح (Correction)، والتقييد (Restriction)، والتصدير (Export)، والمسح (Erasure).
   - توثيق القرارات مع التعليل وأسباب الرفض النظامية أو فرض الحجز القانوني (Legal Hold).
   - التحكم في التزامن المتفائل عبر `expectedVersion`.
2. **تصدير بيانات المرضى الآمن (Secure Patient Export)**:
   - يتطلب تأكيد المصادقة الثنائية خلال آخر 15 دقيقة (`@RequireStepUp(15)`).
   - حماية ضد هجمات حقن المعادلات في الجداول (Formula Injection / CSV Injection).
   - روابط تنزيل مؤقتة ذات صلاحية محددة وعدد تنزيلات أقصى (3 تنزيلات)، مع إمكانية الإلغاء الفوري.
3. **سياسة استبقاء البيانات والتحقق غير التدميري (Retention Policy & Dry-Run)**:
   - حدود دنيا إجبارية للمنصة (الحد الأدنى للتدقيق 90 يوماً، النسخ 30 يوماً، المرضى 180 يوماً).
   - وضع المحاكاة الصارم (`dryRunOnly = true`) دون أي حذف تلقائي للبيانات.
   - تقارير محاكاة إحصائية عبر الدالة الأمنية `lamssa_security.retention_dry_run`.

تفاصيل الحوكمة والتصنيف والحدود في [دليل الخصوصية وحوكمة البيانات](docs/privacy-data-governance.md).

## المتطلبات

- Node.js 24 LTS، بالإصدار `24.15` أو أحدث ضمن السلسلة 24، وnpm 11.
- PostgreSQL 16 محلي عبر مستودعات Linux Mint هو الخيار المفضل؛ Docker Compose اختياري.
- تعتمد الحزم على npm workspaces وملف قفل واحد في الجذر.

الإصدارات المثبتة: NestJS `12.2.0`، Prisma وملحق PostgreSQL الخاص به `7.10.1`،
وpg `8.23.1`. بقيت إصدارات الواجهة كما كانت: React `19.3.1`، Vite `6.4.5`،
TypeScript `5.9.3`. معالجة صور الهوية تستخدم Sharp `0.35.5` المثبّت. لم يُستخدم إصدار Prisma التجريبي المشار إليه بوسم `latest`.

## هوية العيادة وإدارة الفريق — الخطوة 1.9

يفتح المالك أو مدير العيادة **إعدادات العيادة** لإدارة الاسم العربي والاسم الإنجليزي
الاختياري والاسم القانوني والتواصل والعنوان والموقع الاختياري. الحالة للقراءة فقط.
تحتاج تغييرات العملة والمنطقة الزمنية إلى تأكيد صريح، وتُمنع عند وجود سجل مالي
أو جداول وزيارات مرتبطة. تبقى لقطات الفواتير الصادرة كما هي.

محرر الهوية يتيح معاينة الألوان والخط والشعار وأيقونة المتصفح قبل النشر. تُفحص
صور PNG وJPEG وWebP وتُعاد معالجتها؛ لا تُقبل ملفات SVG أو HTML من المستخدم.
تُحفظ الصور الخاصة خارج PostgreSQL في `var/clinic-assets` المتجاهل من Git افتراضيًا،
ولا تُنشر إلا عند حفظ الهوية. الشعارات المنشورة سابقًا تُحفظ للفواتير التاريخية.
يتطلب الإنتاج مخزنًا خاصًا دائمًا ونسخه ضمن خطة النسخ الاحتياطي.

أسماء المنصة الفرعية محجوزة بشكل فريد، وتبقى الأسماء السابقة محفوظة للعيادة.
النطاق المخصص يحتاج إثبات TXT فعليًا؛ **إثبات الملكية لا يعني تفعيل التوجيه**.
DNS للموقع والشهادات والوكيل العكسي مؤجلة. لا يمنح Host أو اسم النطاق صلاحيات عضوية.
يمكن إظهار هوية الدخول العامة عبر `http://localhost:5173/?clinic=ward-demo`.

المالك يدير أدوار الفريق. المدير يستطيع إسناد دور الطبيب وتعطيل عضويات الطبيب
والاستقبال؛ منح الاستقبال أو إعادة تفعيله بصلاحياته المالية يتطلب المالك، ولا يمنح
المدير صلاحيات المالك أو الإدارة أو المحاسبة. آخر مالك نشط محمي؛ تغييرات الأدوار والعضويات تُدقّق
وتنهي جلسات المستخدم مع الإبقاء على عضوياته الأخرى. إرسال الدعوات وقبولها مؤجلان؛
يبقى إنشاء حساب التطوير عبر الأمر المقيّد أدناه. واجهة مدير المنصة منفصلة وللقراءة
فقط، دون إنشاء أو تفعيل أو إيقاف عيادات حتى إضافة ضوابط التشغيل والتدقيق وMFA.

تفاصيل العقود والتخزين والصلاحيات والحدود في [دليل هوية العيادة](docs/clinic-identity.md)،
ونتائج التنفيذ الفعلية في [دليل التطوير](docs/development.md).

## السجل المركزي والنسخ الاحتياطي والتعافي من الكوارث — الخطوة 2.1

نظام متكامل وغير قابل للتعديل لتتبع الأحداث التشغيلية والأمنية، مدعومًا بآلية نسخ احتياطي واستعادة مشفّرة ومختبرة:
- **سجل تدقيق مركزي غير قابل للتعديل (Append-Only)**: يوثق عمليات المصادقة، تغييرات الهوية، إدارة الفريق والأدوار، تحديثات المرضى الإدارية، حجز وإلغاء المواعيد، تسجيل الحضور واستدعاء طابور الانتظار، وإصدار الفواتير وسندات القبض.
- **حجب البيانات الحساسة (PHI & Secret Hygiene)**: تنقية تلقائية تمنع تخزين كلمات المرور، رموز المصادقة، الكوكيز، مفاتيح CSRF، وأرقام البطاقات المصرفية (PAN/CVV)، وأرقام الهويات الوطنية والملاحظات السريرية الطبية.
- **عزل تام متعدد العيادات (RLS Isolation)**: قراءة الأحداث محصورة للمالك ومدير العيادة فقط وفق العيادة النشطة؛ لا يمكن تعديل أو حذف أي سجل عبر الأدوار التشغيلية، ومحمية بواسطة زناد إحباط التعديل (`reject_audit_mutation`).
- **تسجيل الأعطال الأمنية خارج المعاملات**: تسجيل محاولات الدخول الفاشلة ورفض الصلاحيات (403/401) عبر إجراء آمن ومحدد الصلاحية (`record_audit_event`) دون التأثر بتراجع معاملات العمليات الأساسية.
- **واجهة مستخدم عربية مزدوجة**: تتيح إعدادات العيادة التبديل بين «السجل الموحد للعمليات» المزوّد بفلاتر الفئات والتواريخ والصفحات، و«سلسلة بصمات الهوية التشفيرية».
- **نسخ احتياطي مشفّر بـ AES-256-GCM**: يشفّر تفريغ PostgreSQL المعياري (`pg_dump -Fc --enable-row-security`) باستخدام اشتقاق مفاتيح `scrypt`، وصلاحيات ملفات صارمة `0600`/`0700`، وحساب تجزئة SHA-256 مع تدوير تلقائي للنسخ القديمة.
- **تمارين استعادة آمنة ومقاومة للعبث (Drill Mode)**: يتحقق أمر الاستعادة من سلامة التجزئة وبصمة GCM وسلامة بنية الأرشيف وجداول المخطط ضمن بيئة معزولة، ويقيس زمن التعافي (RTO) وعمر نقطة الاستعادة (RPO)، مع حواجز تمنع الكتابة العرضية على قواعد البيانات النشطة.
- **أتمتة النظام عبر Systemd**: ملفات خدمة ومؤقت `lamssa-backup.service` و`lamssa-backup.timer` في `deploy/systemd/` لجدولة النسخ الليلي مع عزل أمني على خوادم لينكس.

أوامر النسخ والاستعادة:
```bash
BACKUP_ENCRYPTION_KEY="your-passphrase" npm run db:backup
BACKUP_ENCRYPTION_KEY="your-passphrase" npm run db:backup:drill
BACKUP_ENCRYPTION_KEY="your-passphrase" npm run db:restore -- --target-db=lamssa_staging
BACKUP_ENCRYPTION_KEY="your-passphrase" npm run assets:backup
BACKUP_ENCRYPTION_KEY="your-passphrase" npm run assets:restore -- --file=/secure/assets.meta.json
```

تفاصيل المعمارية والسياسات في [دليل سجل التدقيق](docs/audit-logging.md) و[دليل النسخ الاحتياطي والتعافي](docs/backup-recovery.md).

## تثبيت المشروع وإعداد البيئة

```bash
nvm use
npm ci
npm run db:env:native
```

ينشئ الأمر ملف `.env` خاصًا بصلاحيات `0600` وكلمات مرور عشوائية منفصلة للتطوير
والاختبار ولأدوار التشغيل والترحيل، ويرفض استبدال ملف موجود. اتبع تعليمات تثبيت
PostgreSQL وإعداد قواعد البيانات في [دليل التطوير](docs/development.md)؛ التثبيت
وتغييرات الخدمة وإنشاء الأدوار تتطلب موافقتك وصلاحيات محلية.
لا ترفع الملف إلى Git ولا تنقل أسرار الخادم إلى إعدادات `VITE_*` العامة.

## تشغيل قاعدة البيانات والخادم

```bash
npm run db:generate
npm run db:validate
npm run db:migrate
npm run db:status
npm run db:migrate:test
npm run db:status:test
npm run db:grant
npm run db:seed
```

الأمر الأخير اختياري: ينشئ هويتين وهميتين لعيادتي ورد ونور بألوان مختلفة دون مرضى
أو مستخدمين أو كلمات مرور. يمكن تكراره دون تكرار السجلات أو إعادة ضبط الهوية المعدّلة.

لإنشاء حساب تطوير محلي، شغّل `npm run auth:provision` وأدخل بريدك واسمك وعضويات
العيادات بصيغة JSON وكلمة مرور تختارها بطول 15–128 حرفًا في الحقل المخفي. مثال عضويات
غير سري: `[{"clinicSlug":"ward-demo","role":"CLINIC_OWNER"},{"clinicSlug":"nour-demo","role":"DOCTOR"}]`.
لا توجد كلمة مرور افتراضية أو صفحة تسجيل عامة. التعديل المقصود لحساب موجود يتطلب
`npm run auth:provision -- --update-existing` ويلغي جلساته. تفاصيل البيئة والأمان في
[دليل التطوير](docs/development.md#step-13-authentication-setup).
إذا كان ملف `.env` من الخطوة السابقة، أضف `AUTH_CSRF_SECRET` عشوائيًا دون استبدال
الأسرار الموجودة، وفق الأمر الآمن في الدليل؛ لا تطبع قيمته.

استخدم PostgreSQL المحلي افتراضيًا. قاعدة Docker الاختيارية للتطوير فقط، بمنفذ مربوط بـ`127.0.0.1` وبيانات محفوظة في وحدة تخزين
مسمّاة. `npm run db:down` يوقفها مع إبقاء البيانات. لا تستخدم إعادة ضبط قاعدة بيانات
أو حذف وحدة التخزين لمعالجة مشكلات الإعداد. إذا لم يتوفر Docker، أنشئ قاعدة تطوير
ومستخدمًا خاصًا في خدمة PostgreSQL محلية واضبط `DATABASE_URL`؛ التفاصيل في
[دليل التطوير](docs/development.md).

لتشغيل الواجهة، في طرفية أولى:

```bash
npm run dev
```

لتشغيل الخادم، في طرفية ثانية:

```bash
npm run dev:api
```

الواجهة عادةً على `http://localhost:5173` والخادم على `http://127.0.0.1:3000`.
استمر باستخدام عنوان الواجهة السابق نفسه، بما يشمل البروتوكول والمضيف والمنفذ،
للوصول إلى بيانات `localStorage` الموجودة. بقي المفتاح `lamssa-clinic-demo-v1`
وشكل البيانات ومنطق وظائف العرض محفوظة؛ لا يوجد حذف أو استيراد تلقائي لبيانات المتصفح.
سجّل الدخول ثم اختر عيادة نشطة لعرض اسمها وألوانها. تستخدم الواجهة وكيل Vite
للطلبات `/api/v1` إلى الخادم المحلي على المنفذ 3000. المعاينة على منفذ مختلف تتطلب
إضافته صراحةً إلى `CORS_ORIGINS` عند تشغيل الخادم؛ راجع دليل التطوير.

للبناء ومعاينة النتائج:

```bash
npm run build
npm run preview
npm run start:api
```

أوامر `dev` و`preview` ما زالت للواجهة، و`build` يبني التطبيقين. يوجد أيضًا
`build:web` و`build:api`. يمكن استخدام
`npm run dev -- --host 127.0.0.1` لتقييد استماع الواجهة محليًا.

## فحص API

```bash
curl -i http://127.0.0.1:3000/api/v1/health
curl -i http://127.0.0.1:3000/api/v1/health/ready
curl -i http://127.0.0.1:3000/api/v1/public/clinics/ward-demo/branding
curl -i http://127.0.0.1:3000/api/v1/public/clinics/nour-demo/branding
```

فحص التشغيل يعيد `{"status":"ok"}` دون الاعتماد على قاعدة البيانات. فحص الجاهزية
يتحقق من الاتصال، ويعيد خطأ 503 عامًا عند تعذره. الهوية العامة تتطلب تطبيق migration
ووجود العيادة؛ تعيد اسم العرض وslug والشعار والألوان فقط لعيادة نشطة. لا تعرض الاسم
القانوني أو الإعدادات الخاصة أو بيانات المستخدمين والعضويات. لا تثبت الهوية العامة
أو النطاق المخصص صلاحية الوصول إلى بيانات العيادة.

الإعداد `CORS_ORIGINS` قائمة عناوين محددة؛ لا يُسمح بـ`*`. يتحقق الخادم من إعدادات
البيئة والمدخلات، ويعيد أخطاء برسائل عربية ورموز ثابتة دون تفاصيل SQL أو أسرار
أو تتبع الاستثناء. توجد مسارات إنشاء وقراءة وتعديل للمرضى؛ توجد مسارات فوترة مالية مقيّدة؛ لا توجد مسارات CRUD عامة للموظفين. توجد مسارات
`/api/v1/auth/{csrf,login,logout,me,clinics,clinic,rotate}` وسياق العضوية
`/api/v1/clinics/:clinicId/me` وإعدادات قراءة مقيّدة بالصلاحية. تتحقق الطلبات الخاصة
من الجلسة والعضوية النشطة والصلاحيات على الخادم. معرّف العيادة أو الدور المرسل من
المتصفح لا يمنح وصولًا.

## الاختبارات والقيود الحالية

```bash
npm test
npm run test:db
npm run test:browser # اختياري؛ يتطلب Chrome وقاعدة الاختبار
```

تختبر المجموعة الأولى سياسة الصلاحيات وCSRF والإعدادات وHTTP وتطبيع المرضى وحسابات توقيت الجدولة
والتوقيت الصيفي ونطاقات التقويم وإلغاء طلبات الواجهة عند تبديل العيادة. أمر المتصفح يستخدم
قاعدة الاختبار وملف متصفح معزولًا وبيانات وهمية مؤقتة، ويختبر المرضى والمواعيد وبقية العروض.
اختبارات قاعدة البيانات تتطلب `TEST_DATABASE_URL` لقاعدة مستقلة طُبّقت عليها migrations
والمنح؛ تُتخطى بوضوح عند عدم ضبطه. تشمل تسجيل الدخول، عزل البيانات وعزل الجدولة،
منع تداخل الأطباء والغرف عبر قيود GiST exclusion، استباقية التعارض، مفاتيح تكرار الحجز،
تراجع إعادة الجدولة، ورفض الوصول بين العيادات تحت FORCE RLS. بيانات القيود
تُلغى بمعاملة، وبيانات المصادقة الوهمية تُنظف بمعرّفات الاختبار فقط.
لا يوجد أمر lint حتى الآن. حالة تطبيق migration والتحقق الفعلي موثّقة في دليل التطوير.

وظائف الخدمة الحالية: المرضى الإداريون، المواعيد والموارد، الزيارات والانتظار، والفواتير والمدفوعات.
العرض القديم الاختياري فقط يحتفظ بحدود بيانات المتصفح، ومنها السداد بقيمة منطقية.
سجل التدقيق المالي الجديد مستقل عن العرض القديم. لا توجد سجلات طبية أو صور أو نسخ
احتياطية مُدارة أو جاهزية إنتاجية؛ ما زالت مراجعة الخصوصية والضرائب والتشغيل مطلوبة.

كلمات المرور تُجزّأ بـArgon2id، والجلسات محفوظة في قاعدة البيانات بمتحققات مجزأة
وسر عشوائي في Cookie من نوع HttpOnly وSameSite، مع Secure وHTTPS في الإنتاج.
حماية CSRF تتحقق من Origin والرمز معًا؛ لا تُحفظ رموز الدخول في localStorage.
الصلاحيات مغلقة افتراضيًا ومنفصلة لكل عضوية؛ الجدول الكامل في وثيقة البنية.

الخطوة 1.4 أضافت وصولًا إلزاميًا عبر معاملات بسياق عيادة موثوق وFORCE RLS على
Clinic وClinicBranding وClinicDomain وClinicMembership. الوصول الخاص يتطلب اختيار
العيادة صراحةً، ثم التحقق من العضوية والصلاحية في كل معاملة. المستخدمون والجلسات
بيانات هوية عامة بمسار داخلي منفصل؛ الهوية العامة لها دالة قراءة محدودة الحقول.
لا يمنح clinicId أو GUC أو نطاق يرسله المتصفح أي صلاحية.

إنشاء حساب التطوير والبذور يحتاج الآن MIGRATION_DATABASE_URL المحلي القائم؛
الخادم يستخدم DATABASE_URL محدود الصلاحيات. لا تُضعف المنح أو RLS لتشغيل الأوامر.
`npm run check:boundaries` يفحص حدود الوصول إلى قاعدة البيانات ضمن البناء والاختبارات.

الخطوة 1.5 أضافت سجل مرضى إداريًا محفوظًا لكل عيادة، مع ترقيم آمن عند التزامن،
بحث ببداية الاسم أو الرقم أو الهاتف، وصفحات محدودة، وتعديل بإصدار لمنع الكتابة فوق
تغييرات الآخرين. الاسم مطلوب، والهاتف والبريد وتاريخ الميلاد والنوع اختيارية.
لا توجد ملاحظات أو صور أو حقول علاجية. يمكن تعطيل الملف وإعادة تنشيطه بصلاحية
patients.update، دون حذف نهائي. تفاصيل API وRLS في دليل التطوير ووثيقة البنية.

الخطوة التالية **1.9: إدارة هوية العيادة والنشر بالعلامة الخاصة**، مع إعدادات آمنة للشعارات

## الزيارات والانتظار المباشر — الخطوة 1.7

- من **طابور الانتظار**: سجّل حضور موعد محجوز أو زيارة دون موعد لملف مريض نشط.
  تحويل الموعد إلى «حضر» ينشئ زيارة ودورًا في المعاملة نفسها. إعادة الطلب لا تكرر الدور.
- الرقم `Q-0001` متسلسل لكل عيادة وتاريخ محلي؛ يبقى ثابتًا عند النقل بين أطبائها وغرفها.
  الأدوار النشطة من يوم سابق تبقى ظاهرة؛ لا يتجاوز منتصف الليل إشغال الطبيب أو الغرفة.
- الاستقبال يستطيع النداء وإعادته والنقل والإلغاء؛ الطبيب يبدأ الخدمة ويكمل الزيارة في
  قائمته المرتبطة بعضويته فقط. لا يصل المحاسب تلقائيًا إلى بيانات الانتظار أو المرضى.
- إكمال الزيارة يغلق الموعد المرتبط معها. الزيارات سجلات حضور إدارية، وليست ملفات علاجية.
- شاشة عامة اختيارية على `/waiting/<clinic-slug>`؛ يفعّلها المالك أو المدير صراحةً.
  تعرض أرقام النداء وتسميات الأطباء والغرف والهوية البصرية فقط، دون أسماء المرضى أو هواتفهم.
  استخدم تسميات موارد مناسبة للنشر العام؛ الشاشة متاحة لأي شخص لديه الرابط بعد التفعيل.
- تحديث SSE آمن مع إعادة تحقق من الجلسة والعضوية، وإعادة مزامنة من API عند الاتصال.
  تحديث احتياطي كل ١٥ ثانية. لا تُحفظ بيانات API أو أسرار الجلسة في تخزين المتصفح.
- الموعد الحاضر قبل هذه الخطوة يُربط بالانتظار صراحةً عبر «تسجيل حضور» ثم اختيار الموعد
  الحاضر. لا يوجد ترحيل جماعي تلقائي. الطابور القديم يبقى خلف «الطابور التجريبي القديم».

بعد تحديث الكود شغّل `npm run db:migrate:test` ثم `npm run db:migrate` و`npm run db:grant`.
لا تتغير ملفات البيئة ولا تُضاف كلمات مرور أو حزم. تفاصيل العقود والسياسات والحدود في
[وثيقة الانتظار](docs/queue.md) و[دليل التطوير](docs/development.md).

## الفوترة والفواتير والمدفوعات — الخطوة 1.8

- **الفواتير** تعرض سجلات API المستقلة للعيادة: مسودة متعددة البنود، خصم لكل بند، ضريبة، إصدار،
  دفعات جزئية أو كاملة وسجل استرداد/عكس مدقّق. لا توجد بوابة دفع خارجية أو بيانات بطاقات كاملة.
- الترقيم `INV-000001` خاص بالعيادة وآمن عند التزامن. لا يمكن تغيير مبالغ أو هوية الفاتورة بعد الإصدار.
- المبالغ أعداد صحيحة بوحدات العملة الصغرى، دون حساب مالي بالفاصلة العائمة أو تحويل العملات.
  العملة ودقتها محفوظتان على كل فاتورة ودفعة؛ تفاصيل التقريب والعملات في [وثيقة الفوترة](docs/billing.md).
- المالك والمحاسب يديران التصحيحات والإلغاء والملخص المالي. الاستقبال ينشئ المسودات ويصدرها
  ويسجّل المدفوعات، دون استرداد أو إلغاء مالي. الطبيب ومدير العيادة لا يملكان صلاحيات مالية ضمن هذا النموذج.
- طباعة فاتورة أو إيصال عربي RTL بهوية العيادة وبيانات المنشأة المجمدة عند الإصدار، مع دعم A4/PDF.
- **الفواتير التجريبية القديمة** تحتفظ بسجلات المتصفح الأصلية دون استيراد أو حذف.
  لا تُخزّن سجلات API المالية في localStorage أو sessionStorage.
- بعد تحديث الكود: `npm run db:migrate:test` ثم `npm run db:migrate` و`npm run db:grant`،
  ثم البناء والاختبارات. لا تُغيّر الأسرار أو تُضف حزمًا جديدة لهذه الخطوة.
- قواعد الضرائب والفوترة النظامية والأرشفة والتوقيع والتسوية المالية تحتاج مراجعة خاصة بسوق التشغيل قبل الاستخدام الحقيقي.
