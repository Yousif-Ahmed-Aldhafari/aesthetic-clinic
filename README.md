# لمسة — Lamssa

منتج لإدارة عيادات التجميل بواجهة **عربية أولًا وباتجاه RTL**، يستهدف عيادات مستقلة
متعددة بهوية بصرية خاصة لكل عيادة. الواجهة الحالية نموذج تجريبي باستخدام React
وTypeScript وVite؛ الخادم NestJS مع PostgreSQL وPrisma، والمصادقة والجلسات
واختيار العيادة والصلاحيات مضافة في الخطوة 1.3.

**لا تُدخل بيانات مرضى حقيقية.** تسجيل الدخول واختيار العيادة يتصلان بالخادم،
أما سجلات المرضى والمواعيد والطابور والفواتير فتبقى بيانات عرض محلية مشتركة بين
اختيارات العيادات في هذا المتصفح؛ ليست سجلات طبية آمنة. عزل RLS مطبّق على موارد العيادة الحالية؛ تجهيز الإنتاج والمراجعة الطبية مؤجلان.

## المتطلبات

- Node.js 24 LTS، بالإصدار `24.11` أو أحدث ضمن السلسلة 24، وnpm 11.
- PostgreSQL 16 محلي عبر مستودعات Linux Mint هو الخيار المفضل؛ Docker Compose اختياري.
- تعتمد الحزم على npm workspaces وملف قفل واحد في الجذر.

الإصدارات المثبتة: NestJS `12.2.0`، Prisma وملحق PostgreSQL الخاص به `7.10.1`،
وpg `8.23.1`. بقيت إصدارات الواجهة كما كانت: React `19.3.1`، Vite `6.4.5`،
TypeScript `5.9.3`. لم يُستخدم إصدار Prisma التجريبي المشار إليه بوسم `latest`.

## تثبيت المشروع وإعداد البيئة

```bash
nvm use
npm ci
npm run db:env:native
```

ينشئ الأمر ملف `.env` خاصًا بصلاحيات `0600` وكلمات مرور عشوائية منفصلة للتطوير
والاختبار ولأدوار التشغيل والترحيل، ويرفض استبدال ملف موجود. اتبع تعليمات تثبيت
PostgreSQL وإعداد قواعد البيانات في [دليل التطوير](docs/development.md)؛ التثبيت
وتغييرات الخدمة وإنشاء الأدوار تتطلب موافقتك وصلاحيات محلية.
لا ترفع الملف إلى Git ولا تنقل أسرار الخادم إلى إعدادات `VITE_*` العامة.

## تشغيل قاعدة البيانات والخادم

```bash
npm run db:generate
npm run db:validate
npm run db:migrate
npm run db:status
npm run db:migrate:test
npm run db:status:test
npm run db:grant
npm run db:seed
```

الأمر الأخير اختياري: ينشئ هويتين وهميتين لعيادتي ورد ونور بألوان مختلفة دون مرضى
أو مستخدمين أو كلمات مرور. يمكن تكراره دون تكرار السجلات أو إعادة ضبط الهوية المعدّلة.

لإنشاء حساب تطوير محلي، شغّل `npm run auth:provision` وأدخل بريدك واسمك وعضويات
العيادات بصيغة JSON وكلمة مرور تختارها بطول 15–128 حرفًا في الحقل المخفي. مثال عضويات
غير سري: `[{"clinicSlug":"ward-demo","role":"CLINIC_OWNER"},{"clinicSlug":"nour-demo","role":"DOCTOR"}]`.
لا توجد كلمة مرور افتراضية أو صفحة تسجيل عامة. التعديل المقصود لحساب موجود يتطلب
`npm run auth:provision -- --update-existing` ويلغي جلساته. تفاصيل البيئة والأمان في
[دليل التطوير](docs/development.md#step-13-authentication-setup).
إذا كان ملف `.env` من الخطوة السابقة، أضف `AUTH_CSRF_SECRET` عشوائيًا دون استبدال
الأسرار الموجودة، وفق الأمر الآمن في الدليل؛ لا تطبع قيمته.

استخدم PostgreSQL المحلي افتراضيًا. قاعدة Docker الاختيارية للتطوير فقط، بمنفذ مربوط بـ`127.0.0.1` وبيانات محفوظة في وحدة تخزين
مسمّاة. `npm run db:down` يوقفها مع إبقاء البيانات. لا تستخدم إعادة ضبط قاعدة بيانات
أو حذف وحدة التخزين لمعالجة مشكلات الإعداد. إذا لم يتوفر Docker، أنشئ قاعدة تطوير
ومستخدمًا خاصًا في خدمة PostgreSQL محلية واضبط `DATABASE_URL`؛ التفاصيل في
[دليل التطوير](docs/development.md).

لتشغيل الواجهة، في طرفية أولى:

```bash
npm run dev
```

لتشغيل الخادم، في طرفية ثانية:

```bash
npm run dev:api
```

الواجهة عادةً على `http://localhost:5173` والخادم على `http://127.0.0.1:3000`.
استمر باستخدام عنوان الواجهة السابق نفسه، بما يشمل البروتوكول والمضيف والمنفذ،
للوصول إلى بيانات `localStorage` الموجودة. بقي المفتاح `lamssa-clinic-demo-v1`
وشكل البيانات ومنطق وظائف العرض محفوظة؛ لا يوجد حذف أو استيراد تلقائي لبيانات المتصفح.
سجّل الدخول ثم اختر عيادة نشطة لعرض اسمها وألوانها. تستخدم الواجهة وكيل Vite
للطلبات `/api/v1` إلى الخادم المحلي على المنفذ 3000. المعاينة على منفذ مختلف تتطلب
إضافته صراحةً إلى `CORS_ORIGINS` عند تشغيل الخادم؛ راجع دليل التطوير.

للبناء ومعاينة النتائج:

```bash
npm run build
npm run preview
npm run start:api
```

أوامر `dev` و`preview` ما زالت للواجهة، و`build` يبني التطبيقين. يوجد أيضًا
`build:web` و`build:api`. يمكن استخدام
`npm run dev -- --host 127.0.0.1` لتقييد استماع الواجهة محليًا.

## فحص API

```bash
curl -i http://127.0.0.1:3000/api/v1/health
curl -i http://127.0.0.1:3000/api/v1/health/ready
curl -i http://127.0.0.1:3000/api/v1/public/clinics/ward-demo/branding
curl -i http://127.0.0.1:3000/api/v1/public/clinics/nour-demo/branding
```

فحص التشغيل يعيد `{"status":"ok"}` دون الاعتماد على قاعدة البيانات. فحص الجاهزية
يتحقق من الاتصال، ويعيد خطأ 503 عامًا عند تعذره. الهوية العامة تتطلب تطبيق migration
ووجود العيادة؛ تعيد اسم العرض وslug والشعار والألوان فقط لعيادة نشطة. لا تعرض الاسم
القانوني أو الإعدادات الخاصة أو بيانات المستخدمين والعضويات. لا تثبت الهوية العامة
أو النطاق المخصص صلاحية الوصول إلى بيانات العيادة.

الإعداد `CORS_ORIGINS` قائمة عناوين محددة؛ لا يُسمح بـ`*`. يتحقق الخادم من إعدادات
البيئة والمدخلات، ويعيد أخطاء برسائل عربية ورموز ثابتة دون تفاصيل SQL أو أسرار
أو تتبع الاستثناء. لا توجد مسارات CRUD للمرضى أو الفواتير أو الموظفين حاليًا. أضيفت مسارات
`/api/v1/auth/{csrf,login,logout,me,clinics,clinic,rotate}` وسياق العضوية
`/api/v1/clinics/:clinicId/me` وإعدادات قراءة مقيّدة بالصلاحية. تتحقق الطلبات الخاصة
من الجلسة والعضوية النشطة والصلاحيات على الخادم. معرّف العيادة أو الدور المرسل من
المتصفح لا يمنح وصولًا.

│       └── test/

لم يُنشأ `packages/shared` بعد؛ عقود المصادقة صغيرة ومحلية للميزة ويمكن استخراجها
لاحقًا. النماذج الحالية: Clinic وClinicBranding وClinicDomain وUser وClinicMembership
وSession وLoginBucket. المستخدم عالمي،
ويمكن أن ينتمي إلى عيادات متعددة بدور مستقل لكل عيادة. صلاحية PLATFORM_ADMIN منفصلة
عن أدوار العضوية، ولا تمنح تلقائيًا الوصول إلى بيانات المرضى.

## الاختبارات والقيود الحالية

```bash
npm test
npm run test:db
```

تختبر المجموعة الأولى سياسة الصلاحيات وCSRF والإعدادات وHTTP مع بديل لقاعدة البيانات.
اختبارات قاعدة البيانات تتطلب `TEST_DATABASE_URL` لقاعدة مستقلة طُبّقت عليها migrations
والمنح؛ تُتخطى بوضوح عند عدم ضبطه. تشمل تسجيل الدخول والجلسات والإلغاء والتدوير
ومنع الوصول بين عيادتين ورفض CSRF وتزوير الأدوار وتعليق العضويات. بيانات القيود
تُلغى بمعاملة، وبيانات المصادقة الوهمية تُنظف بمعرّفات الاختبار فقط.
لا يوجد أمر lint حتى الآن. حالة تطبيق migration والتحقق الفعلي موثّقة في دليل التطوير.

وظائف الواجهة الحالية: لوحة تحكم، إضافة المرضى والبحث، حجز المواعيد وتسجيل الحضور،
طابور غرفة واحدة، وإنشاء الفواتير وتسجيل السداد. بقيت عربية ومتجاوبة ودون مسارات URL.
ما زالت قيود النموذج: تخزين متصفح محدود التحقق، غياب التزامن ومنع تعارض الحجوزات،
مشكلات حدود اليوم المحلي/UTC، أرقام فواتير مشتقة من نتائج العرض، وسداد بقيمة منطقية.
لا توجد سجلات طبية أو حماية صور أو سجل تدقيق أو نسخ احتياطية مُدارة أو جاهزية إنتاجية.

كلمات المرور تُجزّأ بـArgon2id، والجلسات محفوظة في قاعدة البيانات بمتحققات مجزأة
وسر عشوائي في Cookie من نوع HttpOnly وSameSite، مع Secure وHTTPS في الإنتاج.
حماية CSRF تتحقق من Origin والرمز معًا؛ لا تُحفظ رموز الدخول في localStorage.
الصلاحيات مغلقة افتراضيًا ومنفصلة لكل عضوية؛ الجدول الكامل في وثيقة البنية.

الخطوة 1.4 أضافت وصولًا إلزاميًا عبر معاملات بسياق عيادة موثوق وFORCE RLS على
Clinic وClinicBranding وClinicDomain وClinicMembership. الوصول الخاص يتطلب اختيار
العيادة صراحةً، ثم التحقق من العضوية والصلاحية في كل معاملة. المستخدمون والجلسات
بيانات هوية عامة بمسار داخلي منفصل؛ الهوية العامة لها دالة قراءة محدودة الحقول.
لا يمنح clinicId أو GUC أو نطاق يرسله المتصفح أي صلاحية.

إنشاء حساب التطوير والبذور يحتاج الآن MIGRATION_DATABASE_URL المحلي القائم؛
الخادم يستخدم DATABASE_URL محدود الصلاحيات. لا تُضعف المنح أو RLS لتشغيل الأوامر.
`npm run check:boundaries` يفحص حدود الوصول إلى قاعدة البيانات ضمن البناء والاختبارات.

الخطوة التالية **1.5: خلفية إدارة المرضى**، عبر مستودعات وسياسات RLS وحقول إدارية
محدودة واختبارات منع الوصول بين العيادات، دون استيراد تلقائي لبيانات المتصفح. MFA واستعادة الحساب والتدقيق
ومراجعة الخصوصية وتجهيز النشر ما زالت مؤجلة؛ هذه ليست جاهزية إنتاجية. التحقق من DNS وتهيئة SSL والنطاقات المخصصة وربط هوية
العيادة بالفواتير والرسائل مؤجلة إلى خطوات لاحقة.
